# Findings — apx-data

Each entry is something a scenario in `scenarios.md` needed that
the public spec (`apx` at v0.10.0, vendored APDS 4.1) does not define, or
defines ambiguously. Scenarios cite them in `gap=F-DATA-NN` markers so the
runner reports them as known gaps rather than failures. Findings marked
"(upstream APDS)" are issues in the vendored `apds-api-4.1.yaml`, which
APX mounts verbatim and cannot edit; the fix there is an overlay or an
upstream report, never a change to the vendored file.

## F-DATA-01 — `APX-Update-Mode` is not declared

**Where it showed up.** DATA-10, DATA-12, DATA-13, DATA-14, DATA-17,
DATA-19. Part 5 §5.1 makes `APX-Update-Mode: full|change` the switch for
every native `POST`/`PUT`, and Annex A APX-DATA-02 tests it, but the
bundle contains the string nowhere: the data overlay adds `mode` and
`cursor` to the four list routes and nothing to any write. Code generated
from the bundle has no header to send; a linter cannot see the profile.

**Proposed fix.** Add a reusable `components.parameters.UpdateModeParam`
(`in: header`, `name: APX-Update-Mode`, `schema: {type: string, enum:
[full, change], default: full}`, optional) to
`spec/openapi/domains/data/schemas.yaml`, and extend
`apx-data-overlay.yaml` to append it to the `parameters` of every native
`POST` and `PUT` in the eight route families. Optional with a `full`
default, so plain APDS clients are unaffected.

## F-DATA-02 — Change-mode bodies cannot validate against the native schemas

**Where it showed up.** DATA-12 (close a session with identity +
`actualEnd`), DATA-13 (`identifiedVehicle: null`), DATA-14 (stale
change-mode PUT). §5.1 says a change payload "carries identity plus only
the changed fields" and "explicit `null` clears a field". The native
`Session` schema requires `actualStart`, `identifiedCredentials`, and
`segments[]` with `assignedRight` and `validationType`; `identifiedVehicle`
is typed `object`, so `null` is a type error. Every change-mode body in
this module fails validation; the same holds for every other class. The
feed side is fine (`ChangeFeedPage.items` are `type: object`), so the
asymmetry is on writes only.

**Proposed fix.** In `apx-data-overlay.yaml`, for each native `POST`/`PUT`
request body, replace the schema with `oneOf: [<NativeSchema>,
<Class>ChangePayload]`, where the change payload is defined once in the
data domain as `{ required: [id, version], properties: {id, version},
additionalProperties: true }` (optionally per class with each property
re-typed `[<original>, "null"]`). Pair it with F-DATA-01 so the header
selects the branch. Prose: add to §5.1 that a change-mode body validates
against the change payload, not the full entity.

## F-DATA-03 — No 401/403/429 on native routes or the occupancy read

**Where it showed up.** DATA-30 (403 `insufficient-scope` on
`POST /sessions`; 403 `insufficient-grant` on `GET /places/{id}`,
`GET /v1/places/{id}/occupancy`, `GET /places`). Part 9 §9.2–9.3 make
both 403s mandatory on every operation; APX-CORE-07 tests them. None of
the 34 vendored operations declares 401, 403, or 429, and the one APX
route in this class (`/v1/places/{id}/occupancy`) declares only 200 and
404. Same family as F-CTL-07/F-CTL-08, but here the fix cannot be an edit
to the operations.

**Proposed fix.** Extend `apx-data-overlay.yaml` to add the shared
`Unauthorized`, `Forbidden`, and `TooManyRequests` responses
(`application/problem+json`, `Problem`) to every native operation, and
add them inline to `/v1/places/{id}/occupancy` in `apx.yaml`. Register
`unauthenticated` (401) in Part 12 §12.2 (F-CTL-07). Add the Spectral
rule proposed in F-CTL-08 so a secured operation without them fails the
build.

## F-DATA-04 — Stale or foreign cursor: undeclared 404, ambiguous dialect

**Where it showed up.** DATA-07 (cursor older than 7 days), DATA-08
(cursor with a different filter set; cursor from another credential).
§5.2 rules 2 and 5 mandate problem `target-not-found`, but the four feed
routes declare only 200, and Part 12 §12.1 says native routes "keep their
APDS-documented error shapes (`ResponseStatus`)". A server following §12.1
literally returns `{status: "error", code: 404}`; one following §5.2
returns `Problem`. Both are defensible; clients cannot know which to
parse.

**Proposed fix.** In `apx-data-overlay.yaml`, add a 404 response with
`application/problem+json` (`Problem`) to `/places`, `/sessions`,
`/rates`, and `/rights/assigned` `GET`, described as "cursor unknown,
expired, or scoped to another (class, credential, filter set)". State in
§5.2 that cursor errors are APX errors (Problem), since the cursor
parameter belongs to APX, and add that sentence to §12.1 as the one
exception to the native-shape rule.

## F-DATA-05 — Native 409s cannot carry the registered problem types

**Where it showed up.** DATA-11 (`id-collision` with
`Accept: application/problem+json`), DATA-14 (`version-conflict`, same
header). §5.1: "Servers MUST reject a change-mode write targeting a stale
`version` with problem `version-conflict`." APX-CORE-03: "client-supplied
id collision → 409". Part 12 registers both slugs. Every native 409
declares only `application/json` with `ResponseStatus`, so the problem
bodies validate against the wrong schema; the §12.1 sentence "SHOULD
additionally accept `Accept: application/problem+json`" has no declared
response to land on.

**Proposed fix.** In `apx-data-overlay.yaml`, add
`application/problem+json: {schema: Problem}` as a second media type on
every native 400/404/409 (content negotiation by `Accept`), and name the
slug in each 409 description (`id-collision` on POST, `version-conflict`
on PUT). The APDS media type stays first, so a stock client still gets
`ResponseStatus`.

## F-DATA-06 — `extensions` is undeclared on APDS entities

**Where it showed up.** DATA-04 (`apds-ext:apx:ratepolicy@1.0` on a
RateTable), DATA-17 (vendor and APX keys on a Place, full-mode PUT
round-trip, bad key refused). Part 4 §4.3 and Part 3 §3.3 rule 6 say
writers preserve unknown `extensions` keys on every entity; Part 6 §6.6
puts the negotiable flag inside `RateTable.extensions`; APX-CORE-04 tests
the round-trip. Only APX resources declare the property. The vendored
schemas do not forbid additional properties, so payloads pass, but the
key-pattern rule is unenforced (the 400 in DATA-17 has no schema behind
it), generated models drop the container, and readers have no declared
place to look.

**Proposed fix.** In `apx-data-overlay.yaml`, add
`extensions: {$ref: '#/components/schemas/Extensions'}` to
`HierarchyElement`, `Session`, `RateTable`, `RightSpecification`,
`AssignedRight`, `ContactPoint`, and `ObservationElement` (the property
already exists in `common/schemas.yaml`). Purely additive; the pattern on
`Extensions.propertyNames` then does the DATA-17 refusal for free.

## F-DATA-07 — `RateTable` requires two members it does not define (upstream APDS)

**Where it showed up.** DATA-04 (`GET /rates` full list), DATA-19
(`POST /rates`, `GET /rates/{id}`, `PUT /rates/{id}`), DATA-20 (two more
PUTs). `RateTable.allOf[1].required` lists `validityStart` and
`activeTimes`; neither is a property of `RateTable` or of anything it
inherits (the validity window lives in `validity.validityTimeSpecification`,
active times in `RateLineCollection`). Under JSON Schema, `required`
without a matching property still demands the key, so no RateTable — not
even the APDS examples — validates. Every full-mode rate payload in this
module carries a gap marker for this one line.

**Proposed fix.** Report upstream to APDS. Locally, add an action to
`apx-data-overlay.yaml` that sets
`$.components.schemas.RateTable.allOf[1].required` to
`[rateTableName, availability, rateLineCollections]`. The runner already
carries one such relaxation (`Reference` min/maxProperties); this is the
second, and belongs in the build rather than the vetting tool.

## F-DATA-08 — `POST /observations` declares no responses (upstream APDS)

**Where it showed up.** DATA-27. The operation has a request body and no
`responses` object at all, so the runner (and any generator) has nothing
to check a 201 against. Part 13 §13.4 says implementations serving these
writes SHOULD publish `apx.data.observation.created.v1`, so the route is
clearly meant to be served.

**Proposed fix.** Report upstream. Locally, in `apx-data-overlay.yaml`
add `201`, `400`, `409` (`ResponseStatus`, matching the other native
creates) and, per F-DATA-03, the shared 401/403/429.

## F-DATA-09 — `POST /observations` body cannot validate as written (upstream APDS)

**Where it showed up.** DATA-27. The request schema is
`allOf: [{properties: {type: ObservationDataType}}, {oneOf:
[ObservationElement, ObservationSet]}]`, `required: [type]`. The wrapper
constrains `type` to `ObservationElement|ObservationSet`;
`ObservationElement.type` is `CredentialTypeEnum`
(`licensePlate`, `rfid`, …). Both apply, so no value satisfies the
element branch, and the set branch fails on its own required `creator`.
The discriminator mapping also spells the set key `ObvservationSet`. The
`GET /observations` response is unaffected (no wrapper), which is why the
list in DATA-27 validates with `type: licensePlate`.

**Proposed fix.** Report upstream: the wrapper should use a distinct
member (e.g. `observationDataType`) or the credential type on the element
should move to `credentialType`. Locally, an overlay action can replace
the request schema with a plain
`oneOf: [ObservationElement, ObservationSet]` and drop the wrapper, since
the two branches are already distinguishable by their required members.

## F-DATA-10 — `POST /quotes` has no request body; `GET /quotes` is one object (upstream APDS)

**Where it showed up.** DATA-28. `POST /quotes` ("submit a request for a
quote") declares a 200 list of responses and no `requestBody`, so the
`QuoteRightRequest` the scenario sends is undeclared. `GET /quotes` takes
list filters (`place`, `quote_type`, `modified_since`) but its 200 is
`oneOf` the four quote schemas — a single object, not the
`PaginatedListMeta + data[]` shape every other list uses.

**Proposed fix.** Report upstream. Locally, in `apx-data-overlay.yaml`
add `requestBody: oneOf [QuoteRightRequest, QuoteSessionExtensionRequest]`
to `POST /quotes`. Leave the `GET` shape as vendored (changing it would
not be additive) but note in Part 5 that `GET /quotes` returns the single
matching quote.

## F-DATA-11 — The observations change feed is promised but not declared

**Where it showed up.** DATA-27 (`GET /observations?mode=change&cursor=…`).
Part 13 §13.4: "bulk/exactly-once history via the Part 5 change feed
(`mode=change&cursor=…`) on every native route — sessions, rates, rights,
observations". Scenario 07 step 5 sends exactly that request. Part 5 §5.6
and the overlay cover only `/places`, `/sessions`, `/rates`,
`/rights/assigned`; `/observations` has no `mode`, no `cursor`, no
`ChangeFeedPage` branch, and no `page` either.

**Proposed fix.** Either add `/observations` (and, for symmetry,
`/rights/specs`) to the overlay and to §5.6, or correct §13.4 and
Scenario 07 to say the analytics platform gets observations from
`apx.data.observation.created.v1` plus the native time filters. The first
is the smaller change for consumers; observations are the highest-volume
class and the one that most needs a gapless replay.

## F-DATA-12 — `EventData` and `EventTypeEnum` are not in the bundle

**Where it showed up.** DATA-31. Part 5 §5.4 and Part 8 §8.2 say that for
APDS topics the envelope `data` "is the APDS `EventData` shape" and
`EventEnvelope.type` may be "an APDS EventTypeEnum value". The bundler
includes only schemas reachable from mounted paths; APX replaces the APDS
`/webhooks` with its own, so `EventData` (a `oneOf` of the six entity
classes) and `EventTypeEnum` (the eighteen `*Created|Updated|Deleted`
values) drop out. `<!-- apx:validate EventData at /data -->` is
impossible; `ApxEventSubscription.topics` is a free string with no enum
to check the APDS half against.

**Proposed fix.** Reference both from the APX event domain so the bundler
keeps them: `EventEnvelope.data` becomes `oneOf: [EventData, {type:
object}]` (or just a `description` plus an `x-apx-see` link if a `oneOf`
over an open object is judged too loose), and `ApxEventSubscription.topics
.items` becomes `anyOf: [EventTypeEnum, {type: string, pattern:
"^apx\\."}]`. Both additive.

## F-DATA-13 — `modified_since` type: prose says RFC 3339, APDS says epoch

**Where it showed up.** DATA-02. The vendored `modified_since` parameter
is `integer, minimum 0` ("Unix epoch instant"). Public Scenario 03 step 3
sends `modified_since=2026-08-01T00:00:00Z`, which a conforming server
rejects. The scenarios here use the integer.

**Proposed fix.** Correct Scenario 03 to an epoch integer, and add one
line to Part 5 §5.2 rule 3 noting the type, since every APX reader will
assume RFC 3339 from the rest of the standard.

## F-DATA-14 — Response-code irregularities on the native routes (upstream APDS)

**Where it showed up.** DATA-19 (`POST /rates` answers 200 where every
other create answers 201, and declares no 400/409), DATA-23
(`PUT /rights/assigned/{id}` declares 201 "created successfully" — an
upsert — with no 404, while the other PUTs declare 404 and no 201),
DATA-26 (`GET /contacts` and `GET /contacts/{contactId}` alone declare
500). All are declared, so the scenarios cover them, but a client written
to the conventions of one route misreads the next.

**Proposed fix.** Report upstream. Locally, note the three in Part 5 as
known APDS 4.1 behaviour so implementers do not "fix" them and break
stock clients; consider an overlay action adding 400/409 to `POST /rates`
and 404 to `PUT /rights/assigned/{id}` for parity.

## F-DATA-15 — `/places` cannot be filtered to a subtree

**Where it showed up.** DATA-09. §5.2 rule 7: after `grantAdditions` the
client "runs `mode=full` for those subtrees". `GET /places` declares
`place_types`, `place_name`, `place_layer`, `operator`, and geo filters,
but not `place` (the `place_ids` component every other list route
mounts). The only ways to pull one subtree are a geo search or reading
the root by id and walking `childIds` one request per element. An
aggregator fronting forty garages makes the omission expensive.

**Proposed fix.** Extend `apx-data-overlay.yaml` to append
`$ref: '#/components/parameters/place_ids'` to `GET /places` parameters
(subtree-inclusive, as the same filter behaves on `/sessions`). Optional,
so unaffected clients see no change.

## F-DATA-16 — The change branch swallowed every full-mode write

Found 2026-09-28 by probing every `apx:request … invalid` body across the
suite against the schema (the runner skips them). Five native `PUT` bodies
the scenarios call malformed validated, all through the `ChangePayload`
branch that F-DATA-02 added. Fixed in 0.12.2 with a typed change payload per
class: members optional and nullable, scalars typed, `extensions` bound,
unknown members refused. What the schema still cannot tell apart is a
valid partial update from an incomplete full object (an `AssignedRight`
without `rightSpecification`): only the header can, so §5.1a now requires
validators that know it to apply one branch.

## Runner issues

1. **Consecutive `apx:validate` markers over one block are not supported.**
   The prescribed event form — `<!-- apx:validate EventEnvelope -->`
   directly followed by `<!-- apx:validate OccupancySnapshot at /data -->`
   and one ```json block — makes `processFile` report the first marker as
   "apx:validate marker without a ```json block" (`flushDangling` fires on
   the second marker) and validates only the second. Public Scenario 07
   uses exactly this form. Worked around in DATA-27, DATA-29, and DATA-31
   by repeating the block once per marker, with a one-line note; no gap
   marker was used. Fix: let `expect` hold a list of pending validates
   and apply all of them to the next block.
2. **`stripReadOnlyRequired` misses `required` on an allOf parent.** It
   only strips when `required` and `properties` sit on the same node.
   `HierarchyElement` (vendored) puts `required: [type, name, layer,
   hierarchyElementRecord]` on the parent of its `allOf`, with the
   properties inside `allOf[1]`, so the readOnly `hierarchyElementRecord`
   stays required in request bodies. Every other entity in this module
   nests `required` inside the allOf part and is handled. Not worked
   around with a gap marker: a full-mode write is "the complete current
   state" (§5.1), so the place bodies in DATA-16, DATA-17, and DATA-18
   legitimately carry `hierarchyElementRecord` back. A change-mode place
   body would trip it (none is shown; F-DATA-02 covers change bodies
   anyway). Fix: when a node has `required` and an `allOf`, look the
   readOnly flag up through the `properties` of the allOf parts.
3. **False "resolved gap" lines for request-marker gaps.** A `gap=` on an
   `apx:request` marker is settled twice: `checkRequest` (operation and
   query check) settles with its own ctx, then `checkRequestBody` settles
   with a second ctx carrying the same gap. When only the body fails, the
   first settle reports "no longer fails — remove the gap marker" while
   the second reports the gap. Ten such lines appear for this module
   (F-DATA-02 ×4, F-DATA-07 ×4, F-DATA-09, F-DATA-10); all are spurious.
   Exit code is unaffected. Fix: share one ctx across the checks of a
   request marker, or settle only after the body check.
4. **Gapped failures cascade.** A single undeclared `mode` on
   `GET /observations` is reported three times (two query keys plus the
   response schema); the `RateTable` phantom members on `GET /rates` also
   drag in the errors of the `oneOf` alternative. Cosmetic; the gap count
   (26) overstates the distinct defects (15).
5. **Response media type is not selectable.** When a response declares
   both `application/json` and `application/problem+json` (every native
   400/404/409 after the F-DATA-05 fix), `checkResponse` always validates
   against `application/json`, so a problem-dialect body under
   `apx:response 409` fails. DATA-11 and DATA-14 check those two Problem
   bodies with a standalone `apx:validate Problem` instead. Fix: let a
   response marker name the media type (`ct=application/problem+json`),
   or pick `problem+json` when the response declares it and the body has
   `type` and `title`.
