## Why these gaps matter
ADR 0042 makes Nexus Core an APX server and NexPark Edge OS an APX client. NexPark is the "pairing engine": it turns
reads into stays, matches stays to rights, valet tickets, lists and citations, and writes the outcome back as APDS
Sessions and APX Violations. APX says how reads are paired into Sessions is implementation-defined (Part 13
§13.3a(6)), which is right for a single server, but once the pairing engine is a separate client it has to **write**
what it decided, and APX has no place for most of it. The entries below are what the split needs, each verified
against the spec. Entries marked **blocking** stop a migration slice; **edge** stops the Core Edge / sync step (ADR 0042
step 6); **nice-to-have** improves interoperability but has a workaround.

Naming: the proposals use the `apx` namespace because the maintainer can take them into the next edition. If one
ships in Nexus before that, Nexus writes it under the interim partner key `apds-ext:umojo:<name>@1.0` and renames it
when the edition lands (Part 3 §3.3 rule 7, `docs/partner-extension-guide.md`).

## G1. Session read binding written by an external pairing engine
**Problem.** NexPark builds stays from reads and attaches every read to its stay with a role: `sessions.stay_read`
(`src/Nexus.Compliance.Store/Migrations/Sessions/0001_stays.sql:45`, roles `entry | exit | duplicate | activity`,
plus the representative read `sessions.stay.representative_observation_id`, `0001_stays.sql:19`). APX can **read** the
link (`LprRead.session`, `GET /v1/lpr/reads?session=`, Part 13 §13.3a(6)) but nothing lets a client **write** it: APDS
`Session` has no Observation member (only `identifiedCredentials`, `identifiedVehicle`, `segments`), `PUT
/v1/sessions/{id}/plate` cites one Observation for a plate correction only (Part 17 §17.5), and §13.3a(6) leaves pairing
to the implementation. When NexPark is a separate client, Core cannot answer `/v1/lpr/reads?session=` for NexPark's
sessions.

**Checked:** Part 13 §13.3a(6) and (8), Part 17 §17.5, APDS `Session`/`Segment`, `LprRead` (domains/lpr). None carries
a writable read list on a Session.

**Proposed shape.** Level B decoration `apds-ext:apx:session-detail@1.0` on the APDS Session (shared by G1-G4), member
`reads[]`. Written with the native Session `POST`/`PUT` (Part 5); the server derives `LprRead.session` from it and
MUST reject a read already bound to another Session of the same place with 409 `read-already-bound` unless the write
moves it (`supersedes`).

```json
"extensions": {
  "apds-ext:apx:session-detail@1.0": {
    "reads": [
      { "observation": { "id": "0199a0b2-0000-7000-8000-000000000001", "className": "ObservationElement" }, "role": "entry", "representative": true },
      { "observation": { "id": "0199a0b2-0000-7000-8000-000000000007", "className": "ObservationElement" }, "role": "duplicate" },
      { "observation": { "id": "0199a0b9-0000-7000-8000-000000000003", "className": "ObservationElement" }, "role": "exit" }
    ]
  }
}
```
Roles: `entry`, `exit`, `duplicate` (same passage, another camera or frame), `activity` (seen inside, e.g. a sweep).
**Conformance:** `apx-data` (decoration on a native route) with `apx-lpr` (the read-back). **APDS impact:** none; a
plain APDS client ignores the decoration. **Priority:** blocking (the sessions slice of the inventory).

## G2. Session closure provenance: end reason, inferred end, unknown entry, lifecycle state
**Problem.** NexPark records why and how a stay ended: `end_reason` in `exitRead | reentry | stale | parentExit |
review | areaLeft | inventorySweep | exitOnly | valetCheckout` (`Sessions/0006_valet_checkout.sql:8`), `end_inferred`,
flags `entryUnknown`, `orphanExit`, `reentry`, a lifecycle `started | active | ended | closed | disputed`
(`0001_stays.sql:22-26`), and the stale rule that closed it (`stale_closed_rule`). Exit accounting (ADR 0038) closes an
**exit-only** session from an exit read with no entry; APDS `Session.actualStart` is **required**, so such a session
must carry a synthetic start (Nexus uses start = end) and nothing says it is synthetic. Reports exclude exit-only and
stale sessions from compliance and occupancy (ADR 0038, ADR 0044 §2), so a consumer that cannot tell them apart
computes different numbers from the same Sessions.

**Checked:** APDS `Session` (`actualStart` required, no status or reason), Part 5, Part 13 §13.3a(6), Part 22 §22.1
(valet closes "when the APDS Session settles", no reason recorded), `apx-alert-types` (`noCheckOut` is an alert, not a
session property). No end reason, inference flag or lifecycle state anywhere.

**Proposed shape.** Member `closure` of `apds-ext:apx:session-detail@1.0`:
```json
"apds-ext:apx:session-detail@1.0": {
  "lifecycle": "ended",
  "closure": {
    "endReason": "exitOnly",
    "endInferred": false,
    "startObserved": false,
    "rule": null
  },
  "flags": ["orphanExit"]
}
```
- `lifecycle`: `open | ended | final | disputed` (final = no further revision expected; Nexus closes 72 h after exit).
- `endReason`: open code list `apx-session-end-reasons` (new registry) seeded with `exitRead`, `reentry` (same plate
  entered again), `stale` (closed by rule after N hours), `parentExit` (area session closed by its parent), `areaLeft`,
  `inventorySweep` (a sweep found the car gone), `valetHandback`, `exitOnly` (an exit with no observed entry),
  `operator` (a person closed it), `review` (a reviewer paired the exit).
- `startObserved: false` declares `actualStart` synthetic (exit-only); consumers MUST exclude such sessions from
  dwell statistics.
- `rule`: the implementer rule that closed a `stale` session (e.g. `transient-48h`).
**Conformance:** `apx-data`. **APDS impact:** documents a convention for the required `actualStart` on an exit-only
Session; candidate APDS change request "Session end reason" for `docs/apds-change-requests.md`. **Priority:** blocking.

## G3. Match method and vehicle evidence for every link to a Session
**Problem.** Every match NexPark makes carries a method record (ADR 0039, ADR 0040;
`src/Nexus.Compliance.Core/Matching/MatchMethodRecord.cs`): how the plates agreed (`exact | alias | fold | fuzzy |
lenient | reviewer`), the weighted edit cost, whether the plate state agreed, the vehicle evidence level (`unknown |
mismatch | inconclusive | weak | good | strong`) with the log-likelihood ratio and model versions, and whether the match
was applied or only shadowed. It is stored per match type: right (`compliance.match.method_record`,
`Compliance/0010_match_methods.sql:10`), citation (`:11`), valet ticket (`:12`), exit pairing
(`sessions.read_intake.match_method`, `Sessions/0008_match_methods.sql:8`), plate list and inventory sweep. Enforcement
depends on it (lenient matches grant compliance but never issue a citation, ADR 0023 ruling 6), and the portal's method
report and Nexa read it (`GET /v1/match-methods`). APX links a Session to its AssignedRight (`Segment.assignedRight`,
`PUT /v1/sessions/{id}/assigned-right`, Part 14 §14.1b), a Violation to its Session (`relatedSession`) and a ValetTicket
to its Session (Part 22) but never says **how** the link was established or how sure it is.

**Checked:** Part 14 §14.1b (link with `If-Match` and `reason`, no method), Part 6 §6.7 `MatchCandidate` (advisory
candidates for an agent, a score but no method vocabulary, not stored on the link), Part 17 §17.5, Part 19
`relatedSession`/`relatedRight`, Part 22 `ValetTicket.session`.

**Proposed shape.** Member `matches[]` of `apds-ext:apx:session-detail@1.0`, and the same `MatchEvidence` object as
decoration `apds-ext:apx:match-evidence@1.0` on `Violation` (for `relatedSession`) and `ValetTicket` (for `session`):
```json
"matches": [
  {
    "target": { "id": "4b1c0000-0000-4000-8000-000000000042", "className": "AssignedRight" },
    "matchType": "right",
    "plate": { "method": "fold", "editCost": null, "jurisdiction": "agrees" },
    "vehicle": { "level": "good", "llr": 2.31, "model": "nexus-evidence-weights@2026-10-01" },
    "applied": true,
    "decidedBy": "system"
  }
]
```
`plate.method` closed enum `exact | alias | fold | fuzzy | lenient | reviewer`; `vehicle.level` closed enum above;
`matchType` open (`right | valet | violation | list | exitPairing | sweep`); `applied: false` is a shadow match (recorded,
not acted on). No plate characters and no make/model/colour values in the decoration (Part 9 §9.6 minimization).
**Conformance:** `apx-data`; `apx-violations` and `apx-valet` for the shared decoration. **APDS impact:** none.
**Priority:** blocking (without it the split loses the enforcement safety rule and the method report).

## G4. Area (nested) sessions linked to their parent visit
**Problem.** Gated and camera-defined nested areas (ADR 0023 ruling 8) give one car a location session plus area
sessions: `sessions.stay.area_id`, `parent_stay_id`, `minimum_dwell_seconds`
(`Sessions/0002_area_stays.sql:8-12`); an area session closes with `parentExit` when its parent does; reports count
location sessions only (ADR 0044 §1). APDS `Session.hierarchyElement` can name the area, but nothing links an area
session to the visit it is part of, so a consumer double-counts visits.

**Checked:** APDS `Session` and `Segment` (segments split one session by right/rate, not by area), Part 5, Part 13
§13.3a(6) ("a Session is one complete visit"), Part 14.

**Proposed shape.** Members of `apds-ext:apx:session-detail@1.0`:
`"parent": { "id": "…", "className": "Session" }` and `"passThrough": true` for an area stay shorter than the area's
minimum dwell (never scored). Rule: a Session with `parent` MUST have a `hierarchyElement` inside the parent's.
**Conformance:** `apx-data`. **APDS impact:** none. **Priority:** blocking for sites with areas (LAZ 211 has a valet
area).

## G5. Read-level plate correction and review state on LPR reads
**Problem.** A low-confidence read, or any read in a jurisdiction that requires human review, opens a review item
(`events.plate_review`, `src/Nexus.Events/Migrations/0006_plate_review.sql:16`; ADR 0022). A reviewer confirms,
corrects (plate, state, country) or rejects it, with `If-Match` concurrency; the decision feeds stays and the
enforcement-eligibility gate (`GET /v1/observations/{id}/enforcement-eligibility`, used before any enforcement
handoff). Today `Nexus.Events.Api` (Core) owns the queue and the decision endpoint. APX can correct the plate of a
**Session** (`PUT /v1/sessions/{id}/plate`, Part 17 §17.5) and the **access event** of a read (`PUT
/v1/lpr/reads/{observation}/access-event`, §13.3a(4)), but not the plate of a **read**: the correction happens before
any Session exists, one read can feed several sessions (location and area), and enforcement handoff is per read.
`LprReadDetail` has no review state, so a client cannot tell a pending read from a confirmed one.

**Checked:** Part 13 §13.3a(1)-(4) (attributes and confidences; access-event revision only), Part 17 §17.5
(session-level correction; "MUST NOT create a parallel plate store"), Part 19 §19.4 / §19.10
(`unreviewedIssuance` gates issuing a Violation, not a read), `apx-issue-types` (`plateUnresolved` is a resolution
issue, not a read state).

**Proposed shape (core change to §13.3a, new item 4a, mirrors 4):**
- `PUT /v1/lpr/reads/{observation}/plate` with `If-Match`, body `{ "plate": "ABC1234", "country": "US",
  "stateProvince": "TN", "decision": "corrected", "reason": "rear plate legible in frame 3" }`; `decision` is
  `confirmed | corrected | rejected`; the server writes the winning values into `observedCredentialId` /
  `vehicleAncillaryIdentification` and `detail`, increments the Observation `version`, publishes
  `apx.data.observation.updated.v1`, and keeps the engine's original value in `detail.plate.original`.
- `LprReadDetail.review`: `{ "state": "pending | confirmed | corrected | rejected | notRequired", "reasons":
  ["lowConfidence"], "decidedTime": "…" }`, so `/v1/lpr/reads` and the observation events carry it. Reasons are an open
  code list (`lowConfidence`, `noConfidence`, `jurisdictionRequiresReview`).
- Part 19 §19.4 rule 1 gains: an automated detection whose evidence read has `review.state: pending` or `rejected` is
  not issuable when the policy requires review (409 `violation-not-issuable`).
The queue itself (assignment, ordering, reviewer parties) stays implementation-private.
**Conformance:** `apx-lpr`. **APDS impact:** APDS has no route replacing an Observation (same note as §13.3a(4)).
**Priority:** blocking (plate review slice; it is also the open ownership question of the inventory).

## G6. Violations issued by an external enforcement system (citations)
**Problem.** Enforcement vendors (Passport, later AIMS and Trellint) send the citations **they** issued; Nexus
ingests them (`events.citation`, `src/Nexus.Events/Migrations/0008_citations.sql:12`): vendor `source_record_id`
(the citation number), `status` `issued | warned | voided | dismissed`, `payment_status` `unpaid | paid |
partiallyPaid`, `amount_due`, `base_amount`, `amount_paid`, `officer_id`, `violation_code`/`violation_description`,
revisions as the vendor updates them. NexPark later matches each citation to a stay (`compliance.citation_match`,
`Compliance/0007_citation_matches.sql`, `0011_citation_reporting.sql`; `src/Nexus.Compliance/Evaluation/CitationHandler.cs`)
for officer performance and citation reports. Part 19 covers violations **this** server detects and issues, with a
lifecycle that forces `detected → confirmed → issued` through API calls stamped with server time; an already-issued
citation from another system cannot be recorded with its own issue time and status, a partial payment has no
representation (`payment` is one Reference; `paid` is all or nothing), and `relatedSession` cannot be set after
creation (no route updates it).

**Checked:** Part 19 §19.1 lifecycle and rules 1-6, §19.2 endpoints (no PUT/PATCH; `review`, `issue`, `payment`,
`appeals`, `void` only), §19.6 settlement, `Violation` schema (`notice.issuedBy`, `detection.principal`,
`amountHistory` cover officer and escalation; nothing covers external origin or partial payment), Part 18 (moves a
place, not a feed of records).

**Proposed shape.**
1. Core change §19.2: `POST /v1/violations/imports` (adopted in 0.14.0 as `POST /v1/enforcement/violation-imports`, per the §19.2 path rule) (scope `apx.violations:manage`, `Idempotency-Key` REQUIRED, keyed
   on `source.system` + `source.recordId`), accepting a Violation in any state with its `statusHistory[]` times as the
   source reported them; re-posting a newer source revision updates it (version +1, `apx.violations.status.v1`).
2. Decoration `apds-ext:apx:violation-source@1.0`:
```json
"apds-ext:apx:violation-source@1.0": {
  "system": "passport",
  "recordId": "LG-2026-018342",
  "sourceStatus": "partiallyPaid",
  "sourceRevision": 3,
  "receivedTime": "2026-10-04T15:02:11Z"
}
```
3. Core change to `Violation`: `amountPaid` (AmountInCurrency) and `payments[]` (References) alongside `payment`, with a
   rule that `paid` means `amountPaid >= amount`; a partial payment keeps the state `issued`.
4. `POST /v1/violations/{id}/session` (`If-Match`) to set or correct `relatedSession` after creation, carrying the G3
   match evidence.
**Conformance:** `apx-violations`. **APDS impact:** none (net-new surface). **Priority:** blocking (citations slice).

## G7. Change feed on APX-native resource lists
**Problem.** In the separate-servers and edge shapes a module catches up after an outage with `?mode=change&cursor=`
(ADR 0042 §2). Part 5 §5.2 defines the cursor feed on the **native APDS** routes only (`/sessions`, `/rates`,
`/rights/*`, `/observations`, `/places`); `ModeParam`/`CursorParam` are defined in `apx.yaml:5701-5704` but no `/v1`
operation references them. Violations, alerts, valet tickets, commands, credentials and validations are reachable only
through webhooks (24 h retry window, Part 8 §8.3) or SSE resume. NexPark must see Core-ingested citations (G6) and
alerts raised by others, and Core Edge must replay violations and alerts upstream after a long link loss (an air-gapped
site never connects).

**Checked:** Part 5 §5.2 rules 1-7 (native routes), Part 8 §8.3-8.4 (delivery windows), Part 13 §13.4 ("nothing about
a place that APX models is unreachable by feed" lists native routes only), `apx.yaml` path parameters.

**Proposed shape.** Core change §5.2 rule 8: every APX list route of a stateful resource (`/v1/violations`,
`/v1/alerts`, `/v1/valet/tickets`, `/v1/commands`, `/v1/credentials`, `/v1/validations/*`, `/v1/payments`) MUST accept
`mode=change&cursor=` with the same ordering, gaplessness, tombstone and retention rules; reference `ModeParam` and
`CursorParam` from those operations. **Conformance:** each owning class. **APDS impact:** none. **Priority:** blocking
for the separate-servers shape; workaround in a co-located deployment is the Kafka topic.

## G8. Payment detail: base amount, convenience fee, rate applied, rate class
**Problem.** Revenue reports and the rate-deck price check need, per payment, the amount before fee, the fee (LAZ Go
adds $1.25 per transaction: `deploy/dev/places/laz211.yaml` `convenienceFee`), the rate id and name the vendor sold,
the product (`standard | pass | other`) and the class (`standard | validation | discount | zeroed | other`): columns
of `events.parking_right` (`src/Nexus.Events/Migrations/0015_right_rates.sql`), read by `PostgresRevenueReader` and
`GET /v1/revenue` (`src/Nexus.Compliance/Api/RevenueEndpoints.cs`). APX `PaymentRecord.amount` is the total only
(Part 13 §13.6: "line itemization stays APDS-side"); APDS `PaymentLine.paymentType` is `payment | validation` and
`idCode` is a bilateral cost code with no shared vocabulary; neither carries the rate sold.

**Checked:** Part 13 §13.1, §13.1a, §13.6 mapping table, APDS `Payment`, `PaymentLine`, `PaymentTypeEnum`,
`AssignedRight.payments[]`/`rightSpecification`.

**Proposed shape.** Either (a) a registry `apx-payment-line-codes` for `PaymentLine.idCode` (`base`, `convenienceFee`,
`serviceFee`, `tax`, `discount`, `validation`) with a rule that lines sum to the total, plus decoration
`apds-ext:apx:payment-detail@1.0` on the APDS Payment and `PaymentRecord`:
```json
"apds-ext:apx:payment-detail@1.0": {
  "rateSold": { "id": "lazgo-0-1h", "name": "0-1 Hour", "product": "standard", "class": "standard" },
  "lines": [
    { "code": "base", "value": { "amount": 10.00, "currency": "USD" } },
    { "code": "convenienceFee", "value": { "amount": 1.25, "currency": "USD" } }
  ]
}
```
or (b) the same as a core change to `PaymentRecord` (`lines[]`, `rateSold`). (a) keeps APDS untouched. **APDS impact:**
candidate APDS CR for a fee value in `PaymentTypeEnum`. **Priority:** blocking for moving rights and revenue off
`events.parking_right`.

## G9. Concurrent-vehicle limit on a multi-vehicle permit
**Problem.** A monthly account may register several vehicles but park only N at once; NexPark measures and bills the
overage (`permitPools` and `permitPoolBilling` in the place file; `compliance.stay_compliance.permit_account_id`,
`pool_overage`, `Compliance/0006_pool_overage.sql:7-8`; `GET /v1/permit-pool-overage`). APX issues one permit with
many vehicle credentials (Part 14 §14.2, APDS annual-permit pattern) and pools count rights, not vehicles; nothing caps
simultaneous use.

**Checked:** Part 14 §14.2-14.2c (pool availability counts AssignedRights; "the slot is the right, not the
vehicle"), `PermitExtension` (`renews`, `renewedBy`), APDS `AssignedRight` (`instancesAvailable` counts uses, not
concurrency), Part 21 passback (per credential, not per account).

**Proposed shape.** `apds-ext:apx:permit@1.1` adds `maxConcurrentVehicles` (integer ≥ 1) and `overageBilling`
(`{ "mode": "rack | dayRate", "dayRate": AmountInCurrency }`); Part 19 `apx-violation-types` already has
`permitMisuse` for a cited overage. **Conformance:** `apx-permits`. **APDS impact:** none. **Priority:** medium (needed
when permit configuration moves from the place file to Core rights).

## G10. Plate lists (watch, scofflaw, allow, enforcement vehicles)
**Problem.** NexPark keeps per-tenant plate lists with categories and per-location flags (`compliance.plate_list`,
`plate_list_entry`, `plate_list_category_setting`, `Compliance/0005_plate_lists.sql:12-77`; scofflaw details and the
refuse-service flag, `0013_scofflaw_arrivals.sql:16`; ADR 0043). They drive allow-listed compliance (`FROM_LIST`),
watch-list and scofflaw arrival alerts, refused-service signs and enforcement-vehicle visits. ADR 0042 §2 says the
cloud pushes "watch lists and policy downstream" to the edge over APX; APX has no list resource. Credentials (Part 21)
model access media held by a customer, not third-party lists about a plate; the denial reason `accountBalance` covers
a holder's balance, not a scofflaw list from a city.

**Checked:** Part 21 (CredentialRecord, suspend/revoke), `apx-access-denial-reasons` v2, Part 19 §19.10
(policy: notice, caps, escalation; no lists), Part 7 (alerts), Part 14.

**Proposed shape.** New optional class `apx-plate-lists`: `GET/POST /v1/plate-lists`, `GET/PUT
/v1/plate-lists/{id}` (`If-Match`), `GET/POST /v1/plate-lists/{id}/entries`, `DELETE …/entries/{entryId}`, change feed
(G7), topic `apx.platelists.changed.v1`. `PlateList { id, version, name, category, places[], status }`, category from a
registry `apx-plate-list-categories` (`allow`, `watch`, `scofflaw`, `enforcementVehicle`), per-place flags `{ enforced,
alertOnArrival, refuseService }`; `PlateListEntry { id, credential (CredentialTypeEnum + identification), validity,
details { amountOwed, noticeCount, reference } }`, plate values only under a new scope `apx.platelists:read` (Part 9
§9.6), or as a G11 digest for consumers that only screen. **APDS impact:** none. **Priority:** edge (blocking ADR 0042
step 6 if lists are synced through Core; until then they stay NexPark-private).

## G11. Privacy-preserving plate digest
**Problem.** Nexus never puts plate text on an event topic: observations, rights, citations and review decisions carry
a keyed HMAC of the normalized plate (`src/Nexus.Events/PlateProtection.cs:18`, BRD D1), and consumers match by hash
equality (the scofflaw arrival screen indexes list entries by hash and decides in microseconds, ADR 0043 §2; the edge
rights snapshot ships per-location edge hashes, `PlateProtection.EdgeKey` `:31`, `/v1/edge/rights-snapshot` and
`/v1/edge/match-key`, `src/Nexus.Compliance/Api/EdgeEndpoints.cs:24-25`). APX Part 9 §9.6 protects plates only by scope:
a client either holds `apx.lpr:read` and sees the plate, or sees nothing it can match on. A module that only needs
"same plate?" must take full disclosure.

**Checked:** Part 9 §9.6 rules 1-5, Part 13 §13.3a(7), Part 8 §8.7 topic data, Part 21 (credential identification in
clear). No digest or pseudonym concept.

**Proposed shape.** Core change §9.6 rule 6 "Credential digests": a server MAY publish `credentialDigest` (base64url
HMAC-SHA-256 of the normalized identification under a key scoped to (organisation, digest key id)) on Observation,
Session, AssignedRight, Violation and PlateListEntry, through decoration `apds-ext:apx:credential-digest@1.0` `{ "alg":
"HS256", "keyId": "k-2026-10", "value": "…" }`, visible under `apx.data:read`; key distribution to an authorised client
by `GET /v1/digest-keys` (scope `apx.digest:use`, rotation by `keyId`). Normalization rules are the server's and
published in discovery. **APDS impact:** none. **Priority:** medium; edge if Core Edge must keep the hash-only posture
on its local bus.

## G12. Replication profile between a site implementation and an aggregator
**Problem.** ADR 0042 runs a Core Edge at the site and a cloud Core, both APX implementations for the same place at
the same time: the cloud is authoritative for configuration (places, rates, rights, lists, policy), the edge for what
it observed and decided (reads, sessions, violations, commands, alerts), with store-and-forward when the link is down
and, for air-gapped sites, never. Part 18 covers a one-time move of a place from A to B with a single cutover; it does
not cover two implementations sharing a place with authority split by entity class. Replayed writes would be stamped
with the receiver's time (`statusHistory[].time`, `recordInfo`), and idempotency keys and ids from the edge need rules.

**Checked:** Part 18 §18.1-18.5 (move and cutover only), Part 4 §4.1a (identifier locality), §4.2 provenance
(`RecordInfo` has creator and times but no origin implementation), §4.2a idempotent replay, Part 8 §8.2 envelope
`source`, Part 5 §5.2 (cursors server-local).

**Proposed shape.** New Part 18 §18.6 "Replicated site implementations" (normative):
1. An aggregator declares per place and per entity class which implementation is authoritative (`/v1/discovery`
   `replication: [{ place, class, authority: "site" | "aggregator" }]`); a write to a class from the non-authoritative
   side is 409 `not-authoritative`.
2. Replicated writes keep the origin `id`, carry `RecordInfo.origin` (implementation id) and the original
   `creationTime`; lifecycle transitions replayed by a replicator (scope `apx.replication:write`) carry the original
   `statusHistory[].time` and `actor`.
3. Idempotency keys are origin-scoped (`<origin>:<key>`).
4. Each side pulls the other's authoritative classes by change feed (G7 for APX resources) with cursors held by the
   replicator; conflicts on a non-authoritative class resolve to the authority.
**APDS impact:** none. **Priority:** edge (blocking ADR 0042 step 6).

## G13. Templated display content and proof of display
**Problem.** Entry and exit signs show per-vehicle content chosen by scenario (ADR 0029: masked plate, amount, pay QR,
name) through Xibo layouts, and the refused-service sign (ADR 0043) must prove what was shown, when, under which
wording version, and whether the player acknowledged it (`signs.refusal`, `refusal_event`,
`src/Nexus.Signs.Store/Migrations/0002_refusals.sql:32-69`; `POST /v1/sign-refusals/{id}/display-acknowledgements`,
`src/Nexus.Signs/Api/RefusalEndpoints.cs:38`). APX `displayMessage` takes only `message` (MultilingualString, Part 6
§6.1 parameters); `CommandResult` has no display evidence; Part 19 §19.11 `Signage` is static posted signage, not a
per-vehicle dynamic message.

**Checked:** Part 6 §6.1 command parameters and §6.1a `CommandResult` (domains/control), `apx-command-types` v3
(`displayMessage`), Part 19 §19.11.

**Proposed shape.** `displayMessage` optional parameters `template` (Reference or implementer code), `data` (object of
template fields), `holdSeconds`, `wordingVersion`; `CommandResult.display` `{ "shownTime", "contentHash", "screenshot":
imageLink, "acknowledgedBy": "player" | "operator" }`, written when the device confirms. **Conformance:**
`apx-control`. **Priority:** nice-to-have (needed only if signs are driven through Core's command plane instead of
NexPark's own Xibo dispatch).

filtering work today).

## G16. Plate search with the plate in a body, never a URL
**Problem.** `GET /v1/lpr/reads?plate=` (Part 13 §13.3) and the plate-keyed lookups of other Parts put the plate in the
query string, where access logs, proxies, gateways and tracing (`url.query`) keep it, outside the minimization of
Part 9 §9.6. Nexus sends every plate lookup of its own API in a POST body (`/v1/observation-lookups`,
`/v1/plate-lookups`) for that reason. Core serves the APX route as specified (ADR 0042 slice 4), keeps its own
hosting logs from writing the query, and the portal never forwards the APX routes (ruling of 2026-10-06), but any
layer in front of an APX server can still log it.

**Checked:** Part 13 §13.3, Part 9 §9.6, `GET /v1/lpr/candidates`.

**Proposed shape.** `POST /v1/lpr/reads:search` (scope `apx.lpr:read`) with a body `{ plate?, ticket?, observation?,
session?, place?, page? }` and the same response and grant rules as the GET; the GET's `plate` and `ticket` parameters
deprecated, kept for compatibility. The same for every plate- or card-keyed lookup. **Priority:** medium; **blocking**
before the first separate-server deployment (ADR 0042 shape 2), where the call crosses networks and gateways.

## G17. Read-back of one LPR read by path
**Problem.** APX reads one ingested Observation back only as a lookup, `GET /v1/lpr/reads?observation=` (a list), while
the revision route is addressed by path (`PUT /v1/lpr/reads/{observation}/access-event`). A client that holds an id
expects `GET /v1/lpr/reads/{observation}`: one `LprRead`, 404 `target-not-found` when unknown, 403
`insufficient-grant` outside the grant. Core implements only the lookup (ADR 0042 slice 4).

**Checked:** Part 13 §13.3, the bundle's paths (`/v1/lpr/reads`, `/v1/lpr/reads/{observation}/access-event`).

**Proposed shape.** `GET /v1/lpr/reads/{observation}` returning one `LprRead` (scope `apx.lpr:read`), with the lookup
kept. **Priority:** nice-to-have.

## G18. Valet pass type in APDS
**Problem.** A vehicle checked in to valet and read by the LPR must not be enforced. Nexus labels it in APDS as an
`AssignedRight` (the attendant-recorded plate as credential, valid from drop-off to handback) under a valet
`RightSpecification` (ADR 0037 addendum 2026-10-07), so every consumer treats the read as covered. APDS 4.1 cannot say
the pass *is* valet: `RightSpecificationTypeEnum` is `accessPermission | loadingUnloading | oneTimeUseParking |
permitParking | setdownPickup | waiting`, and the only valet term in APDS is the place restriction `valetOnly`. A valet
pass is therefore typed `oneTimeUseParking`, indistinguishable from a transient ticket to a plain APDS consumer
(reporting, an enforcement vendor deciding how to treat a car parked in a `valetOnly` space).

**Checked:** APDS 4.1 `RightSpecificationTypeEnum`, `RestrictionEnum` (`valetOnly`), `RightSpecification`,
`AssignedRight`; APX Part 22 (`ValetTicket` references the Session and, where issued, the AssignedRight: APX-VLT-02).
APX's link identifies the pass only for APX clients.

**Proposed shape.** An APDS change request adding `valet` ("intended for a vehicle in valet custody, valid from
drop-off to handback") to `RightSpecificationTypeEnum`, offered with the other valet items in
`docs/apds-change-requests.md`. Until it lands, APX Part 22 could state that the `RightSpecification` of a
`ValetTicket.assignedRight` is the valet pass type of that place. **Priority:** medium (exemption works without it;
the label is for consumers that do not speak APX).

## G19. All images of a read, and image kinds beyond `overview`/`plate`
**Problem.** An LPR read in Nexus has up to four stills, stored by kind: `plate`, `plateExtended` (a wider plate
crop), `overview` and `context` (`LprImageKinds`, `src/Nexus.Normalization/Mappings/MappingDefinition.cs:115-123`;
ADR 0020). NexPark lists them by kind on the read log and as violation evidence (inventory S1, S17), and an arrival
alert keeps up to four image ids (`src/Nexus.Compliance/Arrivals/ArrivalHosting.cs:43-45`). APDS `Image.imageType` is
`overview | plate` only, and APX's read-back `LprRead` has a single `imageLink`, so a client reading through
`GET /v1/lpr/reads` sees one still and cannot ask for the plate crop. Slice 5 of ADR 0042 needs the full set when
NexPark reads only through APX ([`0042-slice5-plan.md`](0042-slice5-plan.md) §3.8).

**Checked:** APDS 4.1 `Image` (`id`, `image`, `imageLink`, `imageType`, `cameraID`, `cameraDistance`) and
`ImageTypeEnum`; APX Part 13 §13.3 (`LprRead.imageLink`), §13.3b(1) (purge), Part 9 §9.6(2) (access-controlled links).
`ObservationElement.images` is an array, so the Observation can carry every still; `LprRead` cannot.

**Proposed shape.**
- APDS change request: add `plateExtended` ("a wider crop around the plate, showing the plate's surroundings") and
  `context` ("the scene around the vehicle, wider than the overview") to `ImageTypeEnum`, offered with the other items
  in `docs/apds-change-requests.md`.
- Part 13 §13.3: `LprRead.images[]`, each `{ id, imageType?, imageLink?, cameraId? }` with the same access and purge
  rules as `imageLink`; `imageLink` stays as the preferred still for compatibility. Servers SHOULD list every unpurged
  image of the read on both the Observation and the `LprRead`.

Meanwhile Core lists every unpurged image on `Observation.images[]`, typed where APDS can and untyped otherwise; no
extension key. **Conformance:** `apx-lpr`. **Priority:** medium.

## G20. Vehicle attributes of a read whose plate country is unknown
**Problem.** §13.3a(1) requires the winning values of `detail.make`, `.model`, `.color` (and `country`,
`stateProvince`) to appear also in the APDS-native `vehicleAncillaryIdentification`, and APDS 4.1 makes `country`
**required** in that object. A read whose plate country the engine did not report therefore cannot carry make, model
or colour at all in a conformant document; Core drops them (`src/Nexus.Adapters.Apx/ApxLpr.cs:96-101`). NexPark's
vehicle evidence (ADR 0039: make, model, colour against the candidate stay) and the matching scorecard (ADR 0045) lose
their labels on exactly those reads, which are often the hard ones (a plate read too poorly to place).

**Checked:** APDS 4.1 `VehicleAncillaryIdentification` (`required: [country]`), APX Part 13 §13.3a(1) and (7),
`LprReadDetail` (every attribute optional).

**Proposed shape.** Amend §13.3a(1): "The winning values MUST also appear in the APDS-native fields **when the APDS
object can be formed** (its `country` is known); otherwise they appear in `detail` only, and `vehicleAncillaryIdentification`
is omitted." Optionally an APDS change request making `country` optional. **Conformance:** `apx-lpr`. **APDS impact:**
none for the amendment. **Priority:** medium.

## G21. Non-personal read facts under `apx.data:read`
**Problem.** §13.3a(7) puts the whole `LprReadDetail` behind `apx.lpr:*` because it carries the plate and its
candidates. It also carries facts about the passage that identify nobody: `accessEvent`, `movement`, `plateFace`,
`frameReads`, `platesRead`, `captureGroup`. A consumer that must not see plates (a counting display, an occupancy
service, or the plate-withheld event `apx.data.observation.created.v1`) then cannot tell an entry from an exit. NexPark
uses that fact to send only entry reads to the arrival screen and only signed lanes to the sign service, before it
fetches the plate; without it every read costs a plate lookup. Core's withheld output carries `detail` today
(`ApxLprObservationSerializer.cs:65-68`), which is ahead of the rule.

**Checked:** Part 13 §13.3a(3)-(7), Part 9 §9.6(1) (minimization: "plate values appear only under `apx.lpr:*`…"),
Part 8 §8.7 (topic data), `LprReadDetail`.

**Proposed shape.** Amend §13.3a(7): `detail` members are split into **plate-bearing** (`plate`, `alternateReads`,
`plateCategory`, `plateBox`, and the vehicle attributes `make`, `model`, `color`, `bodyType`, `country`,
`stateProvince`) served only under `apx.lpr:*`, and **passage facts** (`accessEvent`, `movement`, `plateFace`,
`frameReads`, `platesRead`, `captureGroup`, `speed`, `engine`) also served under `apx.data:read`, including on the
withheld `apx.data.observation.created.v1`. **Conformance:** `apx-lpr`, `apx-events`. **Priority:** medium.

Meanwhile NexPark uses `detail.accessEvent` when the event carries it and looks the read up when it does not, so a
Core change toward the current §13.3a(7) costs calls, not correctness. No extension key.
